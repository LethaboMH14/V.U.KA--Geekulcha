## 2026-09-26 | Sibusiso, with Claude Code assistant | Incident + fix | Azure's background worker stopped entirely from 15:23 UTC: one unsignable deadline blocked every alert and anchor | PROPOSED

**Research** — Found while checking the VUKA Ledger end to end against Azure. The App Service logs had rotated five times in two hours. From **15:23:57 UTC**, about once a second (around 11,000 times by 17:12 UTC):

```
ERROR:root:worker tick failed
  run_workers.step -> scheduler.tick -> fire_due_for_subject -> append_server -> sign_server_bytes
server.db.DatabaseUnavailable: pinned server signer is unavailable
```

Two causes:
1. **Configuration.** Azure has no `VUKA_SERVER_ED25519_KEY_B64`. `docs/build-log/entries/2026-09-25-ipeleng-key-manifest-bootstrap.md` records that the private half of the pinned server key (`contracts/keys/manifest.json`) was generated by Ipeleng into a scratch file outside the repo, "to be handed to Sibusiso before the server-min deploy". It never reached the App Service. So no server-authored entry can be written on Azure: `no_answer`, `incident_closed`, `answered_late` or `bank_signal_sent`. The bank signal's own request signature can't be made either.
2. **A resilience bug that turned (1) into a total outage.** `run_workers.step()` ran the scheduler first. Once any member had a due deadline whose `no_answer` needed a server signature, the scheduler raised every tick, and the step never reached guardian delivery, bank signals or the anchor coordinator, for any member. Inside the scheduler, one subject's failure also stopped every later subject. That is also why the anchor status had not changed since 15:29: a reset of the stuck batch alone could not have helped.

Separately found: `server/db.py`'s schema-initialisation advisory lock (added earlier today) reused `server/scheduler.py`'s key, 864204. The only effect was a skipped or delayed tick at boot, but it is a real namespace collision.

**Real data / references** — App Service `default_docker*.log` since logging was enabled at 13:14 UTC.

**Business reasoning** — A missing credential must degrade one subject's escalation step, not silently stop every guardian alert on the platform. A guardian not being alerted is the product's worst failure.

**Competitor reference** — Not applicable.

Decision (**PROPOSED**):
- **Scheduler.** `scheduler.tick()` runs each subject's deadline, guardian-removal and contact_lost work in its own transaction and `try`. A failure rolls back that subject only, is retried next tick, and is logged at most once per subject, stage and error per 5 minutes (not once a second).
- **Worker.** `run_workers.step()` also isolates the scheduler and the location purge, so delivery and anchoring always run.
- **Lock key.** `SCHEMA_INIT_LOCK` is now 864205.

Evidence (FACT, real PostgreSQL):
- **`test_an_unsignable_deadline_never_stops_guardian_alerts`** reproduces Azure's exact state (key removed, a due deadline, a pending duress alert). The alert is delivered and the unsignable outcome is left for retry.
- **One test per layer.** `test_the_scheduler_isolates_a_subject_it_cannot_sign_for` checks the tick doesn't raise and the failure is logged once across two ticks. `test_a_scheduler_that_raises_does_not_stop_delivery` checks the step still delivers.
- **Lock keys.** `test_advisory_locks.py` asserts all lock keys are distinct.
- **Mutation-tested.** Removing the scheduler isolation, removing the worker isolation, or restoring the per-tick log each fails its test.

Decision: None accepted.

Needs/blockers: **Sibusiso must obtain the server's Ed25519 private key from Ipeleng** and set it as the App Service setting `VUKA_SERVER_ED25519_KEY_B64` (base64 of the raw 32-byte key). This fix keeps alerts and anchoring running without it, but escalation outcomes, incident closure and bank signals need it. If the key is lost, a new key must be generated and the manifest re-pinned and republished (`0x02`) to Hedera; `verify-pins.json` then changes for the app and the ledger too.

Business handoff: Not applicable.
