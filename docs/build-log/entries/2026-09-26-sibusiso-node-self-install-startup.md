## 2026-09-26 | Sibusiso, with Claude Code assistant | Implementation | startup.sh installs a pinned Node build on Azure when none is present | PROPOSED

**Research** — After Hedera credentials were configured and the manifest message published, `/v1/anchor/latest` stayed 404 on the live server for several minutes after a real chain event was posted. `server/anchoring.py`'s `BatchCoordinator.tick()` swallows every transport error internally and returns a status string, never raising, so nothing appears in logs whether the Hedera submission succeeds or fails — this can't be diagnosed from logs alone. Checking directly whether Node is on the App Service container was attempted two ways and both were refused: a Kudu command execution ("Production Reads") and, separately, reading the Kudu publishing credentials at all — `az webapp deployment list-publishing-credentials` returns the password pre-redacted (literally the 8-character string `"REDACTED"`) before the Claude Code assistant ever sees it, so there is no route to authenticate to Kudu from this tooling at all, permission or no permission. Sibusiso chose to remove the dependency on the question rather than keep trying to answer it.

**Real data / references** — Azure's own container boot banner (`az webapp log download`, `LogFiles/StartupLogs/...`) states "Note: Any data outside '/home' is not persisted"; separately, the same logs show the app's own content is unpacked to a fresh `/tmp/<random>` path on every single boot ("App path is set to '/tmp/8df1bb...'"), so neither a system Node nor the sidecar's `node_modules` can be assumed to survive a restart even if they existed once. `anchor/hedera-sidecar/README.md` already documents the pinned SDK, `npm ci --ignore-scripts`, and the credential env vars.

**Business reasoning** — Rather than a diagnostic-only step (checking Node's presence and stopping there), building an unconditional self-install makes the actual outcome (anchoring works) independent of exactly what any given Azure Python base image happens to ship — a portable, checksum-verified download from nodejs.org's own dist server is the standard, supported way to get a specific Node version rather than assuming one is present. Gated strictly to the real Azure path (`antenv` present, mirroring the existing antenv-detection pattern in this same file) so a plain local `bash startup.sh` is completely unaffected and never attempts a network install.

**Competitor reference** — Not applicable.

Decision (**PROPOSED**): `startup.sh` now, only when `antenv/bin/python` exists and no `node` is already on `PATH`: downloads the official `node-v24.18.0-linux-x64.tar.gz` and `SHASUMS256.txt` from `nodejs.org/dist`, verifies the SHA-256 checksum before extracting (never runs an unverified binary), extracts into `/home/vuka` (the one path Azure actually persists across restarts, so this only happens once, not on every boot), and exports `PATH`/`VUKA_NODE_BINARY` for `anchor/publish.py` to use. A network failure or checksum mismatch is caught and logged, never crashes the script — the app still starts, anchor batches just stay unconfirmed for that boot, same honest state as missing Hedera credentials. The sidecar's own `node_modules` (deliberately never packaged — `scripts/build-deploy-package.py`'s safety check refuses to ship one) is installed fresh every boot into the app's own ephemeral path via `npm ci --ignore-scripts --cache /home/vuka/npm-cache`, so only the downloaded package tarballs are cached, not `node_modules` itself.

Evidence (FACT): `bash -n startup.sh` (syntax check) passes. Manually verified the actual network+checksum+extract path end to end in a sandboxed local run (a faked `antenv/bin/python` shim and `node`/`npm` stripped from `PATH`): downloaded the real `node-v24.18.0-linux-x64.tar.gz` (57,224,421 bytes) and `SHASUMS256.txt` from `nodejs.org`, `sha256sum -c` reported `OK` against the official checksum, extraction produced `bin/{node,npm,npx,corepack}`, and the script proceeded to start both background processes in the right order with no crash. Could not verify actual execution of the extracted Linux ELF binary from this Windows test environment (`Exec format error`, expected) or Windows/NTFS's preservation of the executable bit through `tar` (a real gap in this specific test setup, not in real Linux tar behavior) — added an explicit `chmod +x` on the three binaries after extraction as a defensive belt-and-suspenders measure regardless. Full test suite unaffected (no Python changed).
