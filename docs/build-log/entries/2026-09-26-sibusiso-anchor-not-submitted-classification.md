## 2026-09-26 | Sibusiso, with Claude Code assistant | Bug fix | A process that never started was classified as ambiguous, not "definitely not submitted" | PROPOSED

**Research** — After the Node self-install fix, checking why `/v1/anchor/latest` still 404'd led to re-reading `server/anchoring.py`'s `BatchCoordinator.tick()`. It marks a batch `state='submitted'` *before* calling the publisher, deliberately, and its own comment says the design intent plainly: "An uncertain failure leaves it submitted, never confirmed or resubmitted." Once `state=='submitted'`, every later tick only ever calls `self.reconcile(...)` against the public mirror; there is no code path back to a fresh submission attempt for that batch, ever. That's the right behaviour for a genuinely ambiguous failure (Hedera doesn't provide a global "did I already do this" check, and blindly resubmitting risks a duplicate on-chain message) — but `anchor/publish.py::_publish()` was routing `OSError` (the subprocess never even started — missing binary, permission denied) into that exact same "ambiguous, never retried" bucket as `subprocess.TimeoutExpired` (the process *was* running and might have reached the SDK call before being killed). Those two failures do not carry the same certainty: if the process never started, there is no possible way it reached Hedera. The sidecar's own exit-code-2 signal already gets the correct, retryable treatment (`AnchorNotSubmitted`, which `tick()` marks `failed` and revisits on the next tick) — an `OSError` deserves exactly the same treatment and wasn't getting it.

**Real data / references** — This is very likely not hypothetical: earlier today, before the Node self-install fix landed, `scripts/smoke-live.py` was run against the live Azure server and did enqueue a real `anchor_request` (confirmed via the pending-outbox-kinds check in the earlier `run_workers` test work). At that point `VUKA_NODE_BINARY` wasn't set and no `node` was on the container's `PATH`, so the coordinator's very first submission attempt would have hit exactly this bug: `FileNotFoundError` (an `OSError`) treated as ambiguous, batch marked `submitted` and stuck there permanently, even once Node was fixed.

**Business reasoning** — The fix preserves the system's own conservative philosophy (never auto-resubmit on a genuinely ambiguous failure) rather than loosening it; it only corrects the classification of one specific, unambiguous case that was miscategorised.

**Competitor reference** — Not applicable.

Decision (**PROPOSED**): `anchor/publish.py`'s `except (OSError, subprocess.TimeoutExpired)` is split: `OSError` now raises `AnchorNotSubmitted` (retryable — nothing could have been submitted); `subprocess.TimeoutExpired` keeps raising the plain, ambiguous `AnchorPublicationError` (the process was running and may have reached the SDK call). `AnchorNotSubmitted`'s docstring is broadened to state this explicitly, since the class previously only documented the exit-code-2 case.

Evidence (FACT): `anchor/tests/test_publish.py` — two new tests: a runner that raises `FileNotFoundError` (an `OSError`) must raise `AnchorNotSubmitted`; a runner that raises `subprocess.TimeoutExpired` must raise the plain `AnchorPublicationError`, explicitly not `AnchorNotSubmitted`. Mutation-tested: reverting the split back to the original single `except` clause was confirmed to fail the new OSError test specifically, before restoring the fix. `server/tests/test_anchor_batches.py::test_pre_submit_failure_retries_identical_snapshot_after_60_seconds` already proves, at the coordinator level, that an `AnchorNotSubmitted` batch is correctly revisited and can confirm on a later tick — unchanged by this fix, and now exercised by a real failure mode this fix newly routes into it.

Decision: None accepted.

Needs/blockers, both explicitly **not** addressed by this fix, on purpose — larger design questions, not folded into this scoped change:
1. **A batch that got stuck `submitted` *before* today's fix is not retroactively unstuck by it.** This fix only changes how *future* `OSError` failures are classified; it has no way to reach into `anchor_batches` on the live database and doesn't try to (no DB write access to Azure from this tooling, by design, and this codebase never wants a blind "just resubmit it" script anyway). If the live server does have such a batch from before today, it needs manual inspection: check the pinned topic on the public mirror directly for whether the root was ever actually posted, and only then decide by hand whether to force a resubmission.
2. **A missing `node_modules` for the sidecar (still installing via the backgrounded `npm ci`) is a second, distinct "definitely not submitted" case this fix does not cover.** `cli.mjs`'s top-level `import` of `./publish.mjs` (which itself needs the Hedera SDK from `node_modules`) fails *before* `main().catch()` is even wired up, so Node's own module-resolution error exits with its default code (1), not the sidecar's own exit-code-2 "not submitted" signal — `anchor/publish.py` sees that as `result.returncode != 0`, the same generic, ambiguous `AnchorPublicationError` as a real mid-flight failure. This narrows the exposure window (Node itself installs in ~5s; only the ~100-dependency `npm ci` is slow) but doesn't close it.
3. **There is still no recovery path at all from a genuinely ambiguous failure** (a real `subprocess.TimeoutExpired`, or any receipt-validation failure) — a batch stuck there stays stuck forever by design. Given Hedera consensus finalizes in seconds and the mirror node updates within moments, a bounded-staleness allowance (e.g., after N reconciliation attempts over some safety margin like 15 minutes with nothing found on the mirror, treat it as safe to resubmit) would close this, but it's a real change to a deliberate safety invariant ("None is NOT permission to resubmit") that the team should decide on explicitly, not something to fold into a bug-fix commit.
