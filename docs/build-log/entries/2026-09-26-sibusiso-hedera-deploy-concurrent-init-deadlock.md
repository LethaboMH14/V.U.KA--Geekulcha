## 2026-09-26 | Sibusiso, with Claude Code assistant | Bug fix | Concurrent-boot schema deadlock; deploy packager refusing its own .env.example | PROPOSED

**Research** — Sibusiso set real Hedera testnet credentials (`HEDERA_OPERATOR_ID`/`HEDERA_OPERATOR_KEY`/`HEDERA_SUBMIT_KEY`, the account and pinned topic from the 23 Sep spike — same account, so the operator key is also the topic's submit key) as Azure app settings, then asked to redeploy the branch with today's `run_workers` consolidation. Rebuilding the deploy package first failed outright: `forbidden_path_reason` refused the whole archive over `.env.example`, a secret-free template added earlier today, because its blanket `.env*` prefix check doesn't carve out the one dotfile the repo's own `.gitignore` explicitly allows (`!.env.example`). After fixing that and redeploying, the live container logged a real, reproducible failure on its very next tick: `psycopg2.errors.DeadlockDetected: deadlock detected` from `server/locations.py`'s `purge_closed`, called from `server/run_workers.py`'s `step()`. Root cause: `startup.sh` (26 Sep) now starts both `run_workers.py` and uvicorn concurrently, and both independently call `PostgresDatabase.initialize()` on boot — a single transaction running roughly a dozen `CREATE TABLE IF NOT EXISTS` statements. Two such transactions racing on a brand-new database can deadlock each other; this is a known PostgreSQL limitation, not a driver bug.

**Real data / references** — Reproduced live: `LogFiles/StartupLogs/2026_09_26_..._success.log` from the 09:27 redeploy shows the exact traceback and a genuine `DETAIL: Process ... waits for AccessShareLock ...; blocked by process ...` lock cycle between the two boot processes. The worker's own `try/except` around each tick logged and retried, so the app recovered on the next second — but the failure is real and would recur on every cold start.

**Business reasoning** — A fix that just adds a `time.sleep` stagger in `startup.sh` would hide today's specific two-process case but leave the same race for any other concurrent-boot scenario (a scaled-out App Service, `docker-compose up` bringing up two containers). `server/anchoring.py` already solves an analogous problem with a `pg_try_advisory_lock` around `BatchCoordinator.tick()`; the same session-level advisory-lock pattern, applied to `PostgresDatabase.initialize()`, serializes any number of concurrent callers correctly regardless of what starts them.

**Competitor reference** — Not applicable.

Decision (**PROPOSED**): `forbidden_path_reason(".env.example")` now returns `None` (still refuses every other `.env*` name). `PostgresDatabase.initialize()` wraps its schema-creation transaction in `pg_advisory_lock(SCHEMA_INIT_LOCK)`; the lock is released only by `connection.close()` in `finally`, never by an explicit unlock inside the transaction — an first attempt that DID unlock explicitly, before the transaction committed, let a second caller start creating tables while the first's `CREATE TABLE` statements were still uncommitted, reproducing the race as a `DuplicateObject: type "chain_entries" already exists` error instead of a deadlock. Caught by the new test before it shipped.

Evidence (FACT, real PostgreSQL): `scripts/tests/test_build_deploy_package.py::test_env_example_is_not_treated_as_a_forbidden_environment_file` (new); reverting the fix was confirmed to fail it. `server/tests/test_concurrent_initialize.py::test_concurrent_initialize_on_a_fresh_schema_does_not_deadlock` (new): 6 threads call `initialize()` concurrently against one truly fresh, empty schema — 5/5 clean runs with the fix; removing the lock entirely was confirmed to fail 3/3 with a real `DeadlockDetected`; the intermediate (premature-unlock) version was confirmed to fail consistently too, with `DuplicateObject`, before the final fix. Full suite green on the result (pending this entry's own build-log/CI check).
