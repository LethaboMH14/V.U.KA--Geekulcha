# VUKA.apk account verification — release-blocking review

**Status:** `PROPOSED` review for Sibusiso, then Lethabo; no deployment, credential inspection, provider send or physical-phone retest was done here. **Scope:** the native Android `VUKA.apk` (`za.co.vuka.app`), not the separately published React Native `VIGIL.apk` or `VUKA-next.apk`. **Criterion:** T (technical execution), U (usable onboarding) and S (safety/trust). A real user cannot trust an account screen that offers a verification code the deployed service cannot issue.

## Fine-tooth-comb review before a fix is shipped

1. **The three buttons are not three working identities (`FACT`).** The native [Google chooser](https://github.com/LethaboMH14/V.U.KA--Geekulcha/blob/f9bdb297e2408495c6baf991214cb4c626cecf1f/app/src/main/java/za/co/vuka/app/ui/onboarding/GoogleAccountChooserDialog.kt) selects a fixed example account and explicitly calls itself `SIMULATED`; it does not authenticate with Google. Email and phone converge on the same missing OTP route. Passing that code screen would still not make Google sign-in real. The release and app must not present the chooser as live authentication.
2. **Deploying all of `feature/integrate` is not a safe one-line fix (`FACT`/`PROPOSED`).** The branch contains wider app/server changes and new account storage, not just a provider key. Its account contract is explicitly `PROPOSED` and absent from the accepted §2 requirement/test matrix. Sibusiso and Lethabo must review a bounded deployment diff and migration, with Ipeleng reviewing account authority, retention and provider data flow, before enabling it on Azure. Do not copy a key into Git, a PR or a chat.
3. **Provider success is not delivery proof (`FACT`).** The candidate [`server/notify.py`](https://github.com/LethaboMH14/V.U.KA--Geekulcha/blob/f9bdb297e2408495c6baf991214cb4c626cecf1f/server/notify.py) sends email through Brevo or SMTP and SMS through Twilio only when the relevant settings are present; otherwise it can return `delivery_unavailable`. Its [provider tests](https://github.com/LethaboMH14/V.U.KA--Geekulcha/blob/f9bdb297e2408495c6baf991214cb4c626cecf1f/server/tests/test_notify.py) mock the HTTPS connection and say they do not contact Brevo. An HTTP acceptance response and a green unit test do not prove receipt on an inbox or SA handset. Moreover, `accounts.py` calls the provider **before** inserting the OTP row: a successful send followed by a database failure could leave a received but unverifiable code. The send/store ordering and retry response need a failure-injection test and a reviewed durable-state design. Whether the live deployment has a verified sender, approved SMS sender/trial, and usable settings is **unknown** from this review.
4. **Abuse and leakage remain review gates (`FACT`/`PROPOSED`).** The candidate [`accounts.py`](https://github.com/LethaboMH14/V.U.KA--Geekulcha/blob/f9bdb297e2408495c6baf991214cb4c626cecf1f/server/accounts.py) limits requests per *subject*, but the inspected handler has no per-target or per-IP throttle. New device registrations could evade a subject-only cap and send repeated codes to someone else's contact. The development-code log path is gated only by `VUKA_DEV_OTP_LOG=1`; a production misconfiguration would print codes and recipients. Provider error text can flow back through `delivery_failed`. Ipeleng/Sibusiso should add abuse bounds, a production fail-closed guard for dev logging and safe error redaction before enabling live sends. These are identified code risks, not observed attacks or leaks.
5. **Recovery expectations must be honest (`FACT`).** The native flow and account API are tied to the phone's signing key; a successful email/SMS OTP does not by itself restore an account onto another phone. The accepted spec §9 has a separate recovery-code process. The UI and test plan must not imply that an OTP is account recovery or PIN recovery.
