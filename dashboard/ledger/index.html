    Verify a record

    A member gets their record in VIGIL: Settings → My record → Share with a bank or insurer. That shares the same export JSON the app checks on the phone. Drop it here to check it independently.

    1. 1The member shares their record from VIGIL (My record).
    2. 2They give the file to you: a bank, an insurer, or themselves.
    3. 3You run it here. Your browser recomputes every hash and signature and the Merkle root, then reads the root from Hedera.
    4. 4You keep the fingerprint: root, head, topic, sequence and consensus time.

    Nothing is uploaded. The proof comes from the ANCHOR server and the root from the public Hedera mirror.

    How it works

    The mathematical model

    These are the exact steps this page reruns. Hashes are SHA-256; canon is canonical JSON (spec §5); ‖ joins bytes.

    Commitment
    c = SHA-256(salt ‖ canon(payload))
    The event's kind and details stay private. Only c is in the chain; the salt is 16 random bytes.
    Event hash
    hi = SHA-256(canon(entryi without event_hash))
    Any change to any field of an entry changes its hash.
    Link
    prev_hashi = hi−1,   prev_hash0 = 064
    Each entry names the one before it, so entries cannot be removed or reordered unnoticed.
    Signature
    σi = Signk(canon(statementi))
    The statement binds subject, actor, target, action, source time, key id, counter, event id and c. Device and guardian keys come from the chain; the server key only from the pinned manifest.
    Leaf
    leaf = SHA-256(0x00 ‖ head),   head = hn−1
    One leaf per member chain that changed in the window.
    Node
    node = SHA-256(0x01 ‖ L ‖ R)
    For n leaves, split at the largest power of two below n (RFC 6962). Odd leaves are never duplicated.
    Message
    m = 0x01 ‖ root   (33 bytes)
    The page decodes the Hedera message and requires its 32 bytes to equal the root it recomputed. Key manifests use 0x02 ‖ SHA-256(canon(manifest)).

    A match proves

    • These exact entries existed, in this order, no later than the topic's consensus time.
    • Each entry was signed by the key registered for it, and the server key is the pinned one.
    • Nobody has edited, removed or reordered an entry since.

    It does not prove

    • That the event was real. A signature shows a key was used, not what a microphone heard.
    • That nothing is missing from before the export, or that a compromised server sent every alert.
    • Permanence on testnet. Hedera resets testnet; a re-anchor after a reset is a later record under a new epoch.

    Duress stays private

    A duress PIN is recorded inside a signed commitment, so the chain shows only a hash. The public topic carries one root per window of up to a minute, so anyone watching it sees that something happened in that minute, never whether it was a duress check-in or a normal one. The bank learns of duress separately, through its own bank signal, and can later check that signal against the member's export.
